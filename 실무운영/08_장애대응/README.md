# 장애 대응 기록

## WAS와 서버

### 가상화 서버 장애 때 정상 WAS로 우회

병원 가상화 서버 두 대 중 한 대에 문제가 생겼습니다. 가상화 서버 자체는 병원에서 확인하는 동안, 저는 웹 서버 두 대의 설정을 바꿔 정상 WAS로만 요청이 가도록 했습니다. 병원에서 조치를 마쳤다는 연락을 받고 웹 서버 설정을 원래대로 돌렸습니다.

별도 장애 때는 WAS 한 대가 재부팅됐지만 다른 WAS에서 환자용과 의료진용 서비스가 동작하는 것을 확인했습니다. 병원 쪽 복구 이후 설정을 원복하고 의료진 앱을 확인했습니다. 환자용 앱은 담당자에게 확인을 요청했습니다.

### 서버가 재부팅됐는데 서비스가 올라오지 않은 경우

관리 화면에 접속할 수 없어 서버에 들어가 보니, 재부팅 기록은 있는데 연동 서비스가 떠 있지 않았습니다. 연동 서비스와 전자처방전 서비스를 기동하고 프로세스와 관리 화면을 확인했습니다. 다른 날에는 프록시와 WAS가 각각 한 대씩 재부팅돼, 두 서버의 서비스를 다시 올린 뒤 담당자와 API 및 앱을 확인했습니다.

### 서버에 원격 접속도 되지 않은 경우

모니터링에 알림이 떴지만 관리 화면과 SSH 모두 접속할 수 없었습니다. 병원 담당자가 서버를 부팅한 뒤 접속해 연동 서비스를 올렸고, 관리 화면 접근을 확인했습니다. 다른 장애 때는 병원에서 서버를 재부팅한 뒤 클라우드에서 응답이 돌아오는 것을 확인하고 앱 공지를 내렸습니다.

### 서비스 복구 후에도 DB 복제가 끊겨 있던 경우

가상화 서버 문제로 멈췄던 서비스를 올린 뒤 API와 환자용 앱의 진료시간표 조회를 확인했습니다. 앱은 동작했지만 DB 이중화가 깨져 있어서 병원 담당자에게 별도 작업이 필요하다고 안내했습니다. 물리 서버 장애 때도 병원 측에서 네트워크를 조치한 뒤 원격으로 환자용과 의료진용 서비스를 올렸고, API 확인 뒤 공지를 내렸습니다. DB 복구는 서비스 기동과 별개로 남겨둔 작업이었습니다.

## API와 앱

### 연동 API 커넥션 풀 포화

앱 실행이 안 된다는 요청을 받고 연동 API를 확인했습니다. 지부별 데이터소스 연결이 원활하지 않았고 API 서버의 커넥션 풀이 차 있었습니다. 연동 서비스를 한 대씩 재기동한 뒤 API 주소에 다시 접근되는 것을 확인했습니다. 앱은 담당자에게 테스트를 요청했고, 정상 동작한다는 답을 받았습니다. 데이터소스 연결이 왜 지연됐는지는 별도로 확인이 필요했습니다.

다른 날에는 관리 화면에는 접속됐지만 풀 사용률은 100%였습니다. 연동 서비스를 순차 재기동하고 담당자에게 API 확인을 요청했습니다. API가 정상이라는 회신을 받고 공지를 내렸고, 서버 기동 시간을 확인해 대상 서버가 재부팅된 건 아니라는 점도 전달했습니다. 별도 포화 사례에서는 재기동 후 로그 파일을 백업했습니다.

### API 타임아웃과 관리 화면 502

한 서버에서 API 타임아웃과 응답 지연이 발생해 해당 서버의 서비스를 재기동하고 앱 접속을 확인했습니다. 관리 화면에 502가 나온 다른 사례에서는 같은 증상으로 보더라도 먼저 로그를 확인했습니다. 로그에 연동 서비스가 수동으로 중단된 기록이 남아 있어 서비스를 다시 올렸습니다.

### 여러 병원 앱에서 로그인 실패

여러 병원의 환자용 앱에서 로그인이 되지 않았습니다. 관리자 API 서버를 비교해 보니 한 대에서만 CPU 사용률이 비정상적으로 높았습니다. API 모듈을 순서대로 재기동하고 재확인을 요청해 로그인이 된다는 답을 받았습니다. 다른 로그인 장애 때도 관리자 API를 순차 재기동했고, 담당자들이 여러 병원의 정상 로그인을 확인했습니다. CPU 사용률이 높아진 원인까지 확인한 것은 아닙니다.

### 앱 버전 확인 오류와 헬스체크

여러 병원 앱에서 버전 확인 오류가 났습니다. 공통 API의 애플리케이션이 내려가 있었고 헬스체크 주기도 길게 잡혀 있었습니다. 애플리케이션을 다시 올리고 헬스체크 주기를 조정했습니다. 같은 날 오류가 다시 보고돼 공통 서버 사양을 조정하고 서비스 상태를 모니터링했습니다. 헬스체크 조정만으로 재발이 해결된 건 아니었습니다.

별도 장애 때도 클라우드의 공통 API 모듈이 멈춰 있어 다시 올렸습니다. 모듈이 올라온 것은 확인했지만 중단 원인은 확인하지 못했습니다.

### 앱 보안 모듈 오류

앱 오류가 간헐적으로 나타나 여러 병원 앱에서 같은 증상이 나는지 확인을 요청했습니다. 앱 보안 솔루션을 재기동한 뒤 오류가 잦아든 상태를 확인했습니다. 솔루션 내부 원인까지 확인한 건 아닙니다.

## 네트워크와 접속 경로

### 개발 환경은 정상인데 운영 환경만 접속 불가

클라우드에서는 개발 연동 서버에 연결됐지만 운영 연동 서버에는 접속할 수 없었습니다. 클라우드 쪽 API 상태와 개발 및 운영 경로를 비교해 운영 연동 구간에서 증상이 나는 것을 확인했습니다. 확인한 내용을 담당자에게 전달하고 공지를 올렸으며, 병원에서 조치를 마쳤다는 회신을 받고 공지를 내렸습니다.

### 병원 장비 재부팅 후 도메인 연결 오류

전기 점검 이후 병원 장비가 재부팅되면서 연동 서버 도메인에 연결돼 있던 공인 IP가 바뀌었습니다. 도메인 매핑을 변경한 뒤 서비스 동작을 확인했습니다. 별도 장애 때는 도메인 조회 오류를 확인해 전달했고, 다른 건에서는 운영 연동 서버의 502와 환자용 앱의 조회 오류까지 확인했습니다. 두 건은 장애 구간을 확인한 내용이며 제가 직접 복구한 것은 아닙니다.

### 병원 네트워크 조치 중 API 응답 지연

병원 외부망 장애 상황을 공유하고 앱 공지를 올렸습니다. 클라우드와 병원 연동 구간의 지연이 이어져 클라우드 API를 재기동했고, 직후 운영 앱이 동작하는 것을 확인했습니다. 이후 공지를 다시 올린 기록도 있어 이 조치를 최종 복구로 보지는 않았습니다. 다른 장애에서는 병원 측 네트워크 조치 이후 관리 화면 로그인, API 호출과 앱 실행을 직접 확인했습니다.

## 인증서와 DB 작업

### 인증서를 갱신한 뒤 앱에서 오류가 난 건

인증서 갱신 후 앱에서 오류가 나서 먼저 장애 공지를 올렸습니다. 발급된 인증서의 체인에 문제가 있어 인증서를 다시 생성했고, 클라우드 쪽 JDK에 체인 인증서를 반영했습니다. 공통 API 서버를 한 대씩 재기동한 뒤 담당자에게 앱 테스트를 요청했고, 정상 동작을 확인했습니다.

### 웹 서버 한 대에서 예전 인증서가 보인 경우

클라우드에서 서비스가 만료된 인증서를 내보내는 것을 확인했습니다. 병원 담당자가 웹 서버 한 대에서 예전 인증서가 보인다고 해 해당 서버의 갱신 상태를 확인하고 Nginx를 재기동했습니다. 이후 환자용 앱을 직접 테스트했습니다.

별도 사례에서는 모니터링에서 인증서 만료를 확인하고 갱신한 뒤 API와 앱 테스트를 요청했습니다. 정기 교체 때도 도메인이나 관리자 화면에서 적용 여부를 확인하고, 필요할 때 앱 조회 기능을 테스트했습니다.

### 고객사 DB 작업 이후 앱 확인

환자용 앱의 결제 기능에 타임아웃이 나던 날, 고객사 DB 작업을 맡았습니다. 작업 완료 후 앱 테스트를 요청했고 담당자가 정상 동작을 확인했습니다. 결제 메뉴를 비활성화한 작업은 별도 담당자가 진행했습니다.
